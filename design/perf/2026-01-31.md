# Performance Investigation: Hash+Upload Pipelining

**Date:** 2026-01-31  
**Investigator:** Analysis of Python snapshots vs Rust implementation  
**Status:** Initial findings - needs benchmarking

---

## Investigation Summary

Discovered that Python's snapshots library uses a **pipelined architecture** for hash+upload operations, while Rust uses a **sequential approach**. This may have significant performance implications.

---

## Key Finding: Python Pipelines, Rust Doesn't

### Python Architecture
- **Two ThreadPoolExecutor pools**: READ+HASH pool and UPLOAD pool
- **Concurrent execution**: While File A uploads, File B can be hashing
- **Memory backpressure**: `_MemoryPool` blocks hashing when memory limit reached
- **Single file read**: Data read once, hashed, uploaded, then released
- **Hash deduplication**: Waits for in-flight uploads of same hash

### Rust Architecture
- **Sequential phases**: Hash ALL files first, then upload ALL files
- **Double file read**: Files read once for hashing, again for uploading
- **No memory management**: Relies on CRT for upload buffering
- **No deduplication**: Each file uploaded independently

---

## Performance Implications

### Theoretical Analysis

**Python advantages:**
1. **Better CPU+Network utilization**: Hashing and uploading happen concurrently
2. **Lower latency**: First file starts uploading immediately after hashing
3. **Memory bounded**: Explicit control via `_MemoryPool`
4. **Single I/O pass**: Files read once

**Rust advantages:**
1. **Simpler code**: No explicit pipeline management
2. **CRT optimization**: AWS CRT handles multipart internally
3. **No GIL**: True parallelism for hashing

### Expected Performance Characteristics

| Scenario | Python | Rust |
|----------|--------|------|
| **Many small files** | Steady throughput | Burst hash, then burst upload |
| **Few large files** | Streaming overlap | Sequential phases |
| **Limited memory** | Bounded by pool | May spike during hash |
| **Duplicate files** | Upload once | Upload each |
| **Network latency** | Hidden by pipelining | Exposed in upload phase |

## Design Document Guidance

From `design/manifestv2/2026-01-10-update.md` Section 4.4:

> **Do NOT implement Python's explicit two-pool pipeline.** Instead:
> - Use `tokio::task::spawn_blocking` for CPU-bound hashing
> - Use `buffer_unordered` for concurrent uploads
> - Use `Semaphore` for memory backpressure
> - This is simpler, more idiomatic, and equally efficient

**However:** Current Rust doesn't implement this recommendation either. It uses fully sequential phases.

---

## Proposed Rust Pipelined Approach

```rust
pub async fn hash_upload_manifest(
    manifest: AbsManifest,  // With hash=None for unhashed files
    data_cache: &impl ContentAddressedDataCache,
    options: HashUploadOptions,
) -> Result<(AbsManifest, UploadStatistics), StorageError> {
    // Semaphore for memory backpressure
    let semaphore = Arc::new(Semaphore::new(options.max_memory_permits));
    
    // Process files as stream with bounded concurrency
    let results = stream::iter(manifest.files())
        .map(|file| {
            let sem = semaphore.clone();
            let cache = data_cache;
            async move {
                // Acquire memory permit (backpressure)
                let _permit = sem.acquire().await?;
                
                // Hash on blocking thread (CPU-bound)
                let (hash, data) = tokio::task::spawn_blocking(move || {
                    hash_file_contents(&file.path)
                }).await??;
                
                // Upload (I/O-bound, native async)
                cache.put_object(&hash, file.algorithm, &data).await?;
                
                Ok::<_, StorageError>(file.with_hash(hash))
            }
        })
        .buffer_unordered(options.concurrency)  // Concurrent hash+upload
        .collect::<Vec<_>>()
        .await;
    
    // Build updated manifest with hashes
    // ...
}
```

**Key differences from Python:**
- No explicit thread pools (tokio handles scheduling)
- `spawn_blocking` for CPU work (escapes async runtime)
- `buffer_unordered` for concurrency (built-in)
- `Semaphore` for backpressure (tokio primitive)

## Benchmarking Plan

### Test Scenarios

1. **Small files (1000 files × 1MB each)**
   - Measures: Total time, network utilization, memory usage
   - Expected: Python shows steady throughput, Rust shows phases

2. **Large files (10 files × 1GB each)**
   - Measures: Time to first upload, total time, memory peak
   - Expected: Python starts uploading sooner

3. **Mixed workload (100 small + 10 large)**
   - Measures: Overall throughput, resource utilization
   - Expected: Python better overlap

4. **Duplicate files (50% duplicates)**
   - Measures: Actual uploads vs files processed
   - Expected: Python deduplicates, Rust doesn't

5. **Memory constrained (limit to 512MB)**
   - Measures: Peak memory, OOM behavior
   - Expected: Python bounded, Rust may spike
